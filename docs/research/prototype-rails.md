# Testnet Prototype Rails**Scope.** This is a hackathon-only, self-custodial prototype for Singapore-based clients paying Southeast-Asian freelancers for digital services. It uses test assets only. It must be labelled **"Testnet prototype — no real funds, custody, fiat conversion, or cash-out."**## Fixed recommendationUse **Base Sepolia** (EVM chain ID `84532`) with the public Base Sepolia RPC (`https://sepolia.base.org`), an application-deployed **`DemoUSD`** ERC-20, and user-owned embedded wallets supplied by **Privy**. Base documents Base Sepolia as its public testnet and provides its RPC, explorer, wallet-connection guidance, and several test-ETH faucet options. [Base network connection details](https://docs.base.org/base-chain/quickstart/connecting-to-base) [Base RPC reference](https://docs.base.org/base-chain/api-reference/rpc-overview) [Base faucet list](https://docs.base.org/base-chain/network-information/network-faucets)This combination gives the demo a public, inspectable on-chain trail while retaining an ordinary email/social-login onboarding path. It is also a clean future migration story: Base documents testing USDC payments on Base Sepolia, although that is **not** the recommended demo settlement asset because the agreed product scope is mock-USDT-style settlement. [Base test-payment guide](https://docs.base.org/base-account/guides/accept-payments)### Why not claim test USDT?Do not call the demo asset "USDT" or imply a relationship with Tether. Deploy a plainly labelled, valueless token such as `Escrow Demo USD` (`eUSD`) with **6 decimals** to resemble the amount display users expect from dollar stablecoins. A single test-only minter can allocate a fixed demonstration balance to the buyer wallets; it has no redemption, exchange, or fiat-cash-out feature. Base’s own guide shows deploying a custom ERC-20 to Base Sepolia and verifying it on BaseScan. [Base: launch a token](https://docs.base.org/get-started/launch-token)## Narrow functional path```textEmail / Google sign-in or connected external wallet                  |        user-owned EVM wallet                  |Buyer approves eUSD, then funds one agreement-specific Escrow Vault                  |Seller submits an evidence hash before the milestone deadline                  |Buyer accepts / disputes during configured review window                  |accept or timeout -> seller eUSD       dispute -> resolver's bounded ruling```The product backend stores human-readable agreement text and encrypted/private evidence links if needed; the chain stores only the agreement version/hash, milestone amounts, deadlines, state transitions, evidence hashes, and events. That is sufficient to prove the payment workflow without putting work product or personal information on a public testnet.## Contract pattern: one Escrow Vault per agreementUse a small `EscrowFactory` and a single audited-library-backed `EscrowVault` implementation. For every accepted agreement, the factory creates one independent vault clone and initializes it in the same factory transaction. OpenZeppelin’s `Clones` library implements ERC-1167 minimal proxies; it supports deterministic `CREATE2` deployment and address prediction, which makes one contract address per agreement visible before funding. [OpenZeppelin `Clones` API](https://docs.openzeppelin.com/contracts/5.x/api/proxy)The factory should complete initialization atomically. OpenZeppelin explicitly warns that a clone pointing to an invalid implementation or left uninitialized can be taken over, so an exposed, later initialization transaction is not an acceptable shortcut. [OpenZeppelin clone initialization warning](https://docs.openzeppelin.com/contracts/5.x/api/proxy)Bind the following parameters at initialization (the vault must have no general-purpose administrator that can move milestone money):- buyer wallet, seller wallet, and one resolver wallet;- one accepted ERC-20 token address (`eUSD`) and the milestone amounts;- a versioned agreement hash, one deadline per milestone, and each milestone's configurable review duration;- release/refund state for each milestone and a fee configuration set before funding;- amendment proposal hashes and the two party approvals.For speed, the MVP should use **one ERC-20 only and 2–3 milestones**. An entire agreement is funded once; a milestone release does not affect another milestone's balance.### On-chain rules to demonstrate| Event | Who can call | Contract-enforced result ||---|---|---|| Seller accepts | Seller | Agreement becomes fundable. || Buyer funds | Buyer | Vault pulls the exact total using `transferFrom`; all milestone balances are locked. || Delivery submission | Seller, before deadline | Records `evidenceHash` and starts that milestone’s configurable review window. || Accept | Buyer, during review | Releases that milestone’s fixed amount to the seller. || Silent buyer | Anyone, after review expiry | Calls `autoRelease`; contract releases the milestone to seller. || No delivery | Buyer, after deadline and no submitted evidence | Cancels/refunds only that milestone to buyer. || Dispute | Buyer, during review | Freezes that milestone. || Ruling | Bound resolver | `refundBuyer`, `releaseSeller`, or `split(amountToSeller)`; payout cannot exceed the frozen milestone amount. || Amendment | Both parties | New hash/terms take effect only after both approvals; otherwise prior terms remain. |The contract evaluates dates, signatures/roles, amount bounds, and state—not the quality of creative work. AI may draft the agreement off-chain but has no wallet, resolver, or release permission.### Libraries and safety boundaries- Use OpenZeppelin `IERC20` plus `SafeERC20` for `safeTransferFrom` and `safeTransfer`. The library is specifically designed to handle ERC-20 operations that return `false` or no value. [OpenZeppelin ERC-20 API](https://docs.openzeppelin.com/contracts/5.x/api/token/erc20)- Protect token-moving entry points with `ReentrancyGuard` and apply checks-effects-interactions. OpenZeppelin calls out reentrancy care when control transfers to a recipient. [OpenZeppelin utilities](https://docs.openzeppelin.com/contracts/5.x/api/utils)- Keep roles local to the individual vault: buyer, seller, resolver. Do not grant the platform a withdrawal or ruling role. Where a factory needs a limited configuration role, OpenZeppelin `AccessControl` is the standard role-based option; it also warns that `DEFAULT_ADMIN_ROLE` is highly privileged. [OpenZeppelin access control](https://docs.openzeppelin.com/contracts/5.x/access-control)- No oracle, delivery API, AI decision, upgrade authority, bridge, fiat conversion, or pooled balance belongs in this MVP. A "pause" that can freeze existing user money would undermine the product claim; omit it for the demo rather than implying production-grade emergency governance.## Wallet and onboarding recommendationChoose **Privy user-owned, non-custodial embedded EVM wallets**:1. Offer email or social login and auto-create a user-owned wallet for Web3-new users.2. Also offer “Connect existing wallet” for MetaMask/Coinbase Wallet users.3. Show the wallet address, a testnet badge, and a “Get demo balance” action that allocates `eUSD` from the test token’s demo minter.4. Require the buyer's explicit signature for token approval/funding and each party's signature for relevant on-chain actions. Never use a server signer for release decisions.Privy documents email, social, passkey, and wallet-based authentication, and supports both embedded and external wallets. Its documentation states that user-owned embedded wallets can be non-custodial, with neither Privy nor the application seeing the user's keys; users can export a wallet as an exit path. [Privy key concepts](https://docs.privy.io/basics/key-concepts) [Privy embedded wallets](https://docs.privy.io/wallets/overview/embedded) [Privy wallet export](https://docs.privy.io/wallets/wallets/export)This maintains the project’s intended meaning of self-custody: the user signs from their own wallet, while the independently deployed agreement vault holds the mock tokens only under fixed rules. It does **not** mean the app has created a bank escrow account.## Demo setup checklist1. Claim Base Sepolia test ETH for the deployer and the two demo user wallets from a listed faucet; the currency is only for test gas. [Base faucets](https://docs.base.org/base-chain/network-information/network-faucets)2. Deploy and BaseScan-verify `eUSD`, the vault implementation, and the factory; mint a limited demo balance to the buyer.3. Create one agreement with three milestones and a 72-hour default review window (configure a shorter window only for a live demo).4. Walk through: seller acceptance → buyer funding → evidence hash → buyer acceptance. Run a second, pre-seeded agreement through dispute → resolver split.5. Display each vault address and transaction in Base Sepolia’s explorer, beside the explicit testnet/no-real-value notice.## Deferred decisions- Production token selection and real on/off-ramps.- KYC/KYB, sanctions monitoring, licensed partners, and all regulatory design.- Resolver selection/reputation, appeal mechanics, arbitration, and resolver staking.- Wallet gas sponsorship and account-abstraction optimisation. They are not needed to prove the rules-first escrow flow.
